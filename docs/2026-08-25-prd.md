# punchlist-templates — PRD (v1)

*One repo housing templates + workflows. Agreed 2026-08-25; analysis in
2026-08-25-product-analysis.md.*

## Users

1. **The owner** — curates templates/workflows in Obsidian (this repo is
   a vault), launches workflows, answers needs-input questions, approves
   review steps. Later: authors visually in a web UI.
2. **Agents (claude, hermes, any punchlist actor)** — resolve template/
   workflow refs from tasks, produce output per templates, execute steps,
   ask when stuck. A *workflow-writer* skill helps both humans and agents
   author valid files.

## Repo layout

```
punchlist-templates/
  templates/
    packs/<pack>/<name>.md      # shipped with the product
    authored/<name>.md          # the owner's own
  workflows/
    packs/<pack>/<name>.md
    authored/<name>.md
  runs/                         # (gitignored) advancer state per launched run
  docs/                         # analysis, PRD, this plan
  skills/                       # shippable claude+hermes skills (resolver, writer)
  bin/plt                       # CLI: validate | render | launch | advance | list
  .obsidian/ (gitignored), README, LICENSE
```

## Template format

Markdown + frontmatter:

```yaml
---
name: weekly-review
kind: template
domain: personal            # DOMAINS registry name, optional
inputs:
  - name: week_notes
    exemplar: "raw bullet notes, links, half-thoughts…"
output: markdown            # or json|table|email
tags: [review, writing]
---
## Output shape
<the skeleton the output must follow>
## Golden exemplar
<a complete, real-quality example — REQUIRED, validation fails without it>
```

## Workflow format

```yaml
---
name: research-and-buy
kind: workflow
inputs: [item, budget]
actors: [hermes, owner]
---
steps:
  - id: research
    assignee: hermes
    template: research-brief
    title: "Research {item} under {budget}"
  - id: decide
    assignee: owner          # becomes a review-style human task
    needs: [research]
  - id: order
    assignee: hermes
    needs: [decide]
    on_fail: { retry: 2, then: escalate }   # error chain
  - id: escalate
    assignee: owner
    title: "Ordering failed twice — take over"
```

Edges: `needs` (sequence/join), `when:` (branch on a prior step's
recorded outcome), `repeat_until` (loop), `on_fail` (retry/then). That's
the whole v1 logic vocabulary — anything more is engine-creep.

**Mermaid is generated** (`plt render <workflow>` writes a ```mermaid
block into the file between markers) — renders in Obsidian, GitHub, and
web UIs. Hand-edited diagrams are invalid.

## Runtime (compiler + advancer)

- `plt launch <workflow> --input k=v…` — creates the first step task(s)
  in punchlist via its API; task metadata carries `workflow/run/step/
  template` refs (in the notes tail or a dedicated field if punchlist
  grows one). Run state (which steps done, outcomes) in runs/<id>.json.
- `plt advance` — cron-driven (same rails as the sweeps): looks at
  punchlist for completed/approved step tasks, applies edges, spawns
  next tasks. Pure decision function, table-driven tests.
- Human steps land assigned to the owner (plain tasks); agent steps ride
  the existing queue → screen → claim → finish → review pipeline
  untouched, including vetting and Telegram confirm.

## Needs-input (prerequisite, lands in punchlist core)

Task gains `blocked` status + `question` field; agents block-with-a-
question instead of guessing; "Needs input" lane in the UI + Telegram
brief line; owner's answer stored, task returns to active, advancer
re-offers it with the answer in context.

## Skills

- **plt resolver** (claude + hermes): given a task's refs, load the
  workflow/step/template markdown as driving context; also `plt list`
  browsing ("what templates do we have for research?").
- **workflow-writer** (claude + hermes): interactive authoring helper —
  interviews for goal/actors/steps, writes a valid file (validated by
  `plt validate`), generates mermaid, files it under authored/, reminds
  about golden exemplars. Humans use it conversationally; agents use it
  to propose new workflows from repeated patterns.

## Stories (v1)

1. Owner: "hermes, run research-and-buy for a label printer under $150"
   → workflow launches → tasks appear with refs → hermes researches per
   template → decide-task lands for the owner → approve → hermes orders
   (Telegram confirm fires — high-risk) → done, all visible on the
   Agents board.
2. Owner edits the research-brief template in Obsidian; next run uses it.
3. Hermes hits a login wall mid-step → blocks with "need the vendor
   portal 2FA code" → owner answers from Telegram → step resumes.
4. Owner (or claude) invokes workflow-writer to codify "publish a kb
   article" as a workflow; validate + render pass; it's launchable
   immediately.
5. Claude in CLI: "use the purchase-decision template" → resolver loads
   it → output matches the golden exemplar's shape.

## Non-goals (v1)

Web authoring UI (v2, in the impl plan), timers/schedules (punchlist
recurrence covers), parallel fan-out joins beyond `needs`, cross-machine
run state (runs/ lives on the server host), marketplace/sharing,
non-punchlist backends.
